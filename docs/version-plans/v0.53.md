# v0.53 Core Reset

Status: in progress. Phase 0, the Phase 1 golden fixtures, and Phase 2
landed on 2026-10-23. Sequencing against v0.51
and v0.52 is an owner decision recorded in `docs/roadmap.md`.

## Purpose

v0.40 through v0.52 were all UI, AI, account, or shell releases. Ten plans in a
row (v0.42 to v0.51) carried the non-goal "no renderer, graph, document, or
persistence change". The engine kept every feature working, but each new
feature now costs more than it should:

- A new node type touches about 25 non-test files. A new effect parameter
  touches 10 to 12.
- Topology has two sources: `doc.layers` order and an optional `doc.graph`.
  About 25 call sites build a graph on the fly when it is missing, and layer
  insertion has three code paths.
- `CanvasGraph` keeps a separate array for each of 10 node kinds, so every
  operation on nodes is copied once per kind.
- `EffectLayer` is one flat record with about 110 fields. Which backend runs
  an effect is set by hand-kept key lists.
- `normalizeDocument` runs legacy splitting and migration code on every load.
- Document updates mix `snapshot`, `debounce`, and `silent` writes. Some silent
  writes change user-visible state without an undo entry.

The release thesis is: **adding a node type or an effect parameter is a local
change, and the document has one topology source**. Rendered output stays the
same.

## Scope

Phases land in order. Each phase is a separate PR that keeps the render
fixtures green.

### Phase 0: Process reset and known bugs (done)

- One instruction file: `AGENTS.md`. `CLAUDE.md` and
  `.github/copilot-instructions.md` point to it; `COPILOT.md` is removed.
- Shipped version plans, finished inventories, Fallow baselines,
  `improvement-plan.md`, `ui-overhaul.md`, the old roadmap, and per-release
  evidence moved to `docs/archive/`.
- One release-gate definition (`docs/production-readiness.md`). The release
  verifier no longer requires manual roadmap or production-readiness edits.
- Fixed: splitting a legacy combined effect layer left `doc.graph` pointing at
  the removed layer id, so the split layers were disconnected.
- Fixed: `rgbSplit` ran in both the Canvas 2D worker and a GPU filter, so the
  split was applied twice.

### Phase 1: Safety net

- Done: golden render fixtures for every starter, curated example, and hero
  frame (33 documents), in stack and bootstrapped-graph mode, at preview and
  export size. See `docs/testing.md` ("Golden render fixtures").
  - Pixel hashes are exact, not tolerance-based, and run in the pinned CI
    Playwright container (`npm run test:golden`). Measured macOS vs Linux
    differences from system fonts and emoji reached 21% of pixels, so a
    cross-platform tolerance would hide real regressions.
  - Export at 2x and 3x is a nearest-neighbour upscale of the 1x canvas, so the
    meaningful sizes are preview (540px) and export base size.
  - GPU filter recipes (filter, shader hash, uniforms) are pinned on every
    `npm test`.
- Finding: 18 of 22 stack documents render differently after the editor
  bootstraps a graph for Nodes mode. Documents that rely on `global.bg` without
  a fill layer lose the background in graph mode (mean alpha 122 instead of 255
  on `hero-0`), and effects then run over transparent pixels. Recorded as
  `stackMatchesGraph: false`; Phase 3 must fix it. Not yet checked in the
  browser.
- Remaining: unit tests for `render/layers`, `render/graph` node renderers,
  `effectLayerMigration`, and `renderSignature`.

### Phase 2: Migrations as one-shot steps (done)

- `utils/migrations/` holds `v1ToV2`, `v2ToV3` (with the AI-shader GLSL code
  generation in `legacyAiShaderGlsl.ts`), and a new `v3ToV4` step, registered in
  `MIGRATIONS`. Each has a fixture test; the generated legacy GLSL is pinned
  byte for byte.
- `DOCUMENT_SCHEMA_VERSION` is 4. The 3 -> 4 step took over every legacy branch
  `normalizeDocument` used to run on each load: `kind: 'source'` aliases,
  0-100 material percentages, removed shader kinds (and `staticMeshGradient`
  distortion), and combined effect splitting with graph rewiring.
  `normalizeDocument` now only fills defaults and validates
  (`documentPersistence.ts` 1140 -> 710 lines).
- Golden fixtures also assert that `normalizeDocument` does not change the
  pixels or GPU recipe of any shipped document.
- Changed from the original plan: hero frames and effect thumbnails keep
  building layers from multi-effect patches. The field-ownership rules are not
  legacy; they moved to `utils/effectPresetPatch.ts` (authoring helper) and
  will be derived from the effect parameter schema in Phase 5.
- Compatibility: builds before v0.53 reject schema 4 documents and share links
  ("Unsupported document schema version"). Release notes must say so.

### Phase 3: Graph is the only topology source

- Schema v5: `doc.graph` is always present. A stack document is a graph whose
  shape `isLayerStackGraph` recognizes; the layer list is a view of it.
- Remove the inferred-graph fallbacks, the three-way layer insertion, and the
  silent graph bootstrap on mode switch and camera change.
- Reduce `graphMode` to `stack | graph`.

### Phase 4: Node-kind registry

- `CanvasGraph.nodes: Record<id, GraphNode>` with a `kind` discriminant
  replaces the per-kind arrays (migration in Phase 2 style).
- One definition module per node kind holds its type, defaults, normalizer,
  renderer, render signature, inspector, and Add Library entry. Generic code
  iterates the registry.

### Phase 5: Effect parameter schema

- Declare effect parameters in a schema: key, default, zero value, range, step,
  backend (`canvas | worker | gpu`), and control type.
- Derive `DEFAULT_EFFECT_LAYER_PROPS`, `ZERO_EFFECT`, the backend key lists,
  inspector controls, randomization ranges, effect docs, and render signatures
  from the schema.

### Phase 6: Commands, history, and cleanup

- One command dispatcher. Each command declares its history policy. No silent
  write may change user-visible state.
- Undo/redo goes through the dispatcher instead of the raw setter.
- Split `types/config.ts`, `render/layers/index.ts`, `render/graph.ts`,
  `documentPersistence.ts`, and `useDocumentRenderer.ts` along the seams the
  registries create.
- Delete code that only tests use, after Fallow trace validation.

## Non-Goals

- No new node kinds, effects, AI features, or UI surfaces.
- No intentional change to rendered pixels. A fixture diff in Phases 1-6 is a
  bug unless the plan is amended first.
- No visual redesign of the editor. UI changes are limited to wiring inspectors
  and Add Library to the registries.
- No backend, account, or backoffice change.
- No GPU visual-regression suite (that needs its own tolerance plan).

## Acceptance Criteria

- [x] Phase 0: one agent instruction file, `docs/` holds only current docs plus
      `docs/archive/`, and the two known bugs have regression tests.
- [ ] Golden fixtures cover all starter, hero, and example documents in stack and
      graph mode, and pass unchanged at the end of every phase (fixtures exist
      since Phase 1).
- [ ] `stackMatchesGraph` is `true` for every golden case.
- [x] `normalizeDocument` contains no legacy-format branches; each migration is
      a versioned step with a fixture test.
- [ ] `inferLinearGraph` is called only from the schema v5 migration.
- [ ] Adding a node kind is one new definition module plus one registry entry,
      proven by moving an existing kind (grime shadow) into the registry
      without touching generic files.
- [ ] Adding an effect parameter is one schema entry plus its render code,
      proven by a test that every schema key has exactly one backend and a
      control.
- [ ] No production call to the raw document setter outside the dispatcher, and
      no silent write that changes visible state.
- [ ] No production source file over 800 lines in `utils/`, `types/`, or
      `hooks/`.

## Validation

- `npm run check`
- `npm run build`
- `npm run test:browser`
- `npm run perf:node-editor` for Phases 3, 4, and 6 (node editor paths)
- `npm run test:golden` on every phase PR (CI job `render-golden`)

## Rules During The Reset

- A phase PR may change engine internals freely. It may not change rendered
  output, the stored document format without a migration, or user-visible
  behavior.
- New feature work that needs a new node kind or effect parameter waits for
  Phase 4 or Phase 5, so it lands on the registry instead of adding another
  copy.
